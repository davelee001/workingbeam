[![CI](https://github.com/davelee001/workingbeam/actions/workflows/ci.yml/badge.svg)](https://github.com/davelee001/workingbeam/actions/workflows/ci.yml)

WorkingBeam is a privacy-focused freelancer payment and custodial escrow platform
built around the Beam blockchain payment rail.

## Demo flow

**Freelancer &rarr; Create Request &rarr; Client Pays &rarr; Escrow Funded &rarr; Work Submitted &rarr; Client Releases &rarr; Payment Confirmed**

1. The freelancer creates a payment request with the work, amount, client, and due date.
2. The client reviews and approves the request.
3. The client pays through the Beam wallet rail.
4. WorkingBeam records the funds in custodial escrow.
5. The freelancer submits the completed work and delivery note.
6. The client reviews the delivery and releases the payment.
7. Both parties see the confirmed Beam transaction.

## Run the demo

Load the populated demo workspace and start both services:

```powershell
npm run demo:no-install
```

Open `http://localhost:3000/auth`, then choose **Demo as Freelancer** or **Demo as Client**. The demo accounts share the password `Password123!` when manual sign-in is needed.

## Deployment on Render

The frontend and backend are defined in `render.yaml` and ready to provision through a Render Blueprint.

| Service | Type | Build | Public endpoint |
| --- | --- | --- | --- |
| `workingbeam-demo` | Static React site | `npm ci && npm run build` | Assigned after Blueprint provisioning |
| `workingbeam-api` | Node web service | `npm ci && npm run build` | Assigned after Blueprint provisioning |

The API health check is `/api/health`. The static site rewrites application routes to `index.html` and uses `REACT_APP_API_URL` to reach the API across origins.

Configure these server environment values before deploying:

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `SMTP_URL`
- `EMAIL_FROM`
- `BEAM_WALLET_API_URL`
- `BEAM_WALLET_API_KEY`
- `BEAM_ESCROW_ADDRESS`

`VERIFICATION_CODE_PEPPER` and `WALLET_ENCRYPTION_KEY` are generated by Render from the Blueprint. Escrow is custodial, so use a production Beam Wallet API and escrow address before handling real funds.

The Blueprint configures `CLIENT_ORIGIN` and `REACT_APP_API_URL` for the proposed Render service names. Confirm the assigned service URLs in the Render dashboard after provisioning and update these values if Render assigns different hostnames.

> Deployment status: Blueprint-ready. Do not advertise the hosted demo as live until both the frontend and `/api/health` return successful responses.

## Mobile experience

Mobile users get a bottom navigation bar for Home, Payments, Requests, Notifications, and Profile.

The public mobile Menu button includes a three-line hamburger icon before the word Menu.
When opened, the mobile Menu button changes to a Close/X state and exposes Sign in, theme switching, and Get started actions.

Freelancers also get a floating Request Payment action that opens the payment request form in one tap.

The mobile Overview prioritizes:

- Available balance
- Pending payments
- Active escrow
- Recent transactions

Secondary detail remains available through dedicated screens.

Payment states use color-coded badges for Pending, Funded, Released, and Disputed.
On mobile payment request cards, the QR code is the primary focus with amount, Share, and Copy Link actions.
Payment request cards include a five-step workflow stepper: Request Created, Client Paid, Work Submitted, Release Payment, and Complete.
The public workflow section uses a pink/magenta-forward palette with the custodial Protect step visually highlighted.
Workflow cards use green hover treatment so users can clearly see the active step against the pink resting palette.
Public secondary call-to-action buttons use a pink Beam-inspired treatment to balance the dark green hero palette.

## Security and appearance

WorkingBeam defaults to a dark Beam-inspired interface.
Users can switch to light mode from the authentication screen, public header, dashboard header, or settings.
Desktop public pages include a compact icon-only theme switch near the sign-in action.
Mobile public menus include Sign in and Get started actions.
Mobile users switch public-site appearance from inside the Menu dropdown.
Desktop public navigation keeps authentication actions out of the header, leaving only the compact theme icon.
Theme preference is saved locally so the selected mode remains after refresh.
Primary actions and navigation controls use touch-friendly 44-48 px targets.
Supported browsers can enable device unlock through passkeys, Face ID, or fingerprint prompts.
Device unlock is a browser-supported convenience layer and normal email/password sign-in remains available.
The Settings screen summarizes appearance and device-unlock readiness for workspace users.
The public website follows the same dark-first visual identity with an optional light presentation.
The mobile public call-to-action section uses a visible pink action button with larger tap sizing.

## Presentation demo

Keep the presentation focused on the seven-stage [demo flow](#demo-flow). Use the freelancer and client demo buttons to switch roles while the payment status badge, QR code, and escrow stepper show progress toward confirmation.

## Security boundaries

- Protect wallet credentials and user data.
- Never expose server secrets to the client.
- Preserve payment-state validation.
- Add tests for all financial actions.
- Use the Beam mock wallet only in development.

WorkingBeam uses custodial escrow. Beam provides the private payment and confirmation rail, while WorkingBeam controls the escrow lifecycle and release workflow.
